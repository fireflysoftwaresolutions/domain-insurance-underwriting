# Governed quote owner connection

The five scoped quote operations invoke the real Core Underwriting generated SDK. They do not turn submission CRUD into an underwriting decision or bind/issue a policy. Existing submission code, canonical data and SQL remain unchanged. Concrete service/factory implementations end in Impl; interfaces, DTO/config records, conventional Controller/Configuration classes and generated SDKs retain their roles.

The new routes require genuine issuer/JWKS and Domain-audience authentication. They never install a permit-all chain. Explicitly select the owner connection with `insurance.quotes.governed-client.enabled=true`. Configure `api-configuration.core-insurance.governed-quotes` fields: base-path, registration-id, issuer, jwk-set-uri, domain-audience, core-audience, tenant-claim, delegating-client-claim and delegating-client-id. No endpoint, client, audience, claim-name or business-program default is supplied. HTTP is accepted only with explicit allow-loopback=true and an exact loopback host. Production HTTPS endpoints cannot contain userinfo/query/fragment or path normalization aliases.

The configured Spring client registration must use native TOKEN_EXCHANGE and CLIENT_SECRET_BASIC, declare the same issuer and expected delegating client ID, and permit the actual quote operation scopes. Secrets stay in the normal external Spring client configuration, never in this record or a request body. The required scope names come from the actual Core QuoteAuthorityGate: offer, accept, read, history:read and recover under insurance:quotes; recovery additionally requires read. A per-operation native registration requests only the needed subset. Output scopes must include that subset and cannot exceed the original verified caller scopes. This permits narrowing, never privilege creation.

The adapter uses Spring7.1.1 WebClientReactiveTokenExchangeTokenResponseClient and TokenExchangeGrantRequest. The subject is the exact current verified JwtAuthenticationToken matching the inbound bearer, not a machine principal. The native grant carries requested Core audience and no fabricated actor token. Native JWT signature/issuer/audience validation checks the returned access token. HUMAN kind, issuer, opaque subject, signed party and opaque platform tenant remain equal; no UUID inference, tenant translation, fake nbf or changed lifetime is accepted. Optional genuine nbf remains optional. Output audience is exactly the one configured Core audience; its client claim must match the configured registration. Requested/issued token type is access_token. Provider support and matching issuer policies/client permissions must be established separately; source support is not provider acceptance.

One monotonic5-second call window covers principal/registration lookup, native exchange/verification, SDK execution, response validation and final caller/time checks. The native admission phase also has a2-second ceiling, with no renewal. Current JWT and exchanged expiry only narrow the window. This narrows the existing owner caps and does not reset any Core budget. Redirects and proxies are disabled on owned grant/SDK transports, token responses are bounded16KiB, native token body extraction uses suppressed logging hints, and raw errors/credentials never become caller messages. A fresh ApiClient/authentication belongs to each call; no authorized-client cache keyed by principal name is used.

Offer/accept capture all original scalar fields once per subscription before asynchronous exchange. Owner action/intent/scope association is checked without reimplementing financial canonical hashes. All four typed owner outcomes are preserved. Empty, mismatched or unclassified completion is a fixed502 with no protected result, raw cause or new action ID. This means outcome unconfirmed, not refusal/absence/rollback or permission to retry a new action. Post-call authority loss also yields an unconfirmed result. Initial actual400/401/403 statuses remain explicit; generic owner503 is not manufactured into a safe pre-work503. Reads/recovery never issue writes or fabricate absence. All five routes disable HTTP response idempotency caching.

Service tests isolate capture/response behavior behind the transport port while still using genuine generated SDK clients. Infra tests use the native grant client, actual RSA-signed synthetic tokens and native JWT decoders over controlled exchanges; they do not claim real issuer acceptance. The normal combined Core→Domain→Experience build must generate the genuine SDKs before compiling consumers. Public Core's existing tenant/nbf gate, mandatory Product/configuration ports, optional schema installation, provider/client/PDP deployment and physical positive quote→bind→issue remain separate gates. No database or Domain persistence is introduced here.
